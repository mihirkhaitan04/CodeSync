CodeSync Interview Guide — Part 3
MERN Mastery & Advanced Design (Q76-Q100)

SECTION 13: MERN STACK & JAVASCRIPT DEEP-DIVE

Q76: What does MERN stand for, and how do the pieces fit together in CodeSync?

MERN stands for MongoDB, Express, React, Node.js.
• React handles the UI (the Code Editor, Video UI).
• Node.js is the runtime environment that executes JavaScript on the server.
• Express is the framework running on Node.js that handles our API routes (/api/login, /api/execute/code).
• MongoDB is the NoSQL database storing our user credentials and profiles.

Q77: Is JavaScript synchronous or asynchronous?

JavaScript is a synchronous, single-threaded language by default. However, Node.js and web browsers provide Web APIs (like setTimeout, fetch, or database queries) that allow it to behave asynchronously. The Event Loop manages pushing these asynchronous callbacks back to the main thread once they finish, preventing the main thread from blocking.

Q78: Explain Promises and async/await.

A Promise represents the eventual completion (or failure) of an asynchronous operation. It has 3 states: Pending, Fulfilled, or Rejected.
async/await is syntactic sugar over Promises, making asynchronous code look synchronous and easier to read. In CodeSync, we use it everywhere: 
const handleRun = async () => {
  try {
    const res = await fetch("/api/execute/code", {...});
    const data = await res.json();
    setOutput(data.output);
  } catch (error) { ... }
};

Q79: What is the difference between == and === in JavaScript?

== checks for value equality but performs type coercion (e.g., "5" == 5 is true). === checks for strict equality (both value and type must match; "5" === 5 is false). In CodeSync, we strictly use === to prevent unexpected bugs.

Q80: What is a closure in JavaScript? Where is it used in CodeSync?

A closure is a function that remembers the variables from its lexical scope even after the outer function has finished executing. In CodeSync, every time we use useState or define an event handler inside a functional component, we are relying on closures.
However, stale closures are a known issue with Socket.io in React. If a socket listener is set up in a useEffect, it captures the state variables as they were on the initial render. This is why we use useRef (e.g., valueRef.current) to always access the latest code value inside socket callbacks.

SECTION 14: ADVANCED SECURITY & CLOUD

Q81: Why do we care about hashing passwords if the MongoDB database is hosted securely in the cloud?

Even if MongoDB Atlas is highly secure, insider threats, accidental leaks, or application-level SQL/NoSQL injections can expose the database. If passwords are stored in plain text (as they currently are in CodeSync), a leaked database immediately compromises every user's account. Because people reuse passwords across sites, a breach in CodeSync could let hackers access a user's Gmail or bank account. Hashing with bcrypt ensures that even if the database is fully exposed, the passwords cannot be reverse-engineered.

Q82: What is a Man-in-the-Middle (MITM) attack, and how do we prevent it?

A MITM attack occurs when an attacker intercepts communication between the client and server. In CodeSync, if a user logs in over HTTP, their plain-text password and JWT token can be stolen on a public Wi-Fi network. We prevent this by enforcing HTTPS (TLS/SSL), which encrypts all data in transit.

Q83: Explain the difference between Authentication and Authorization.

Authentication is verifying WHO you are (e.g., logging in with username and password). CodeSync handles this via POST /api/login.
Authorization is verifying WHAT you are allowed to do (e.g., an interviewer can kick a user, but an interviewee cannot). CodeSync currently uses a lightweight authorization system based on the status state ("interviewer" vs "interviewee") stored in sessionStorage.

SECTION 15: REACT PERFORMANCE & ADVANCED HOOKS

Q84: Why is React considered fast? (Explain Reconciliation)

React is fast because manipulating the real DOM is expensive. React maintains a Virtual DOM (a lightweight JavaScript representation of the DOM). When state changes, React builds a new Virtual DOM, compares (diffs) it against the previous one, and calculates the minimum number of changes needed. It then batches these changes and updates the real DOM in one highly optimized step. This process is called Reconciliation.

Q85: What are React dependencies in the useEffect hook?

The dependency array [socket, roomId] tells React exactly when to re-run the effect. If the array is empty [], the effect runs exactly once on mount. If a dependency (like roomId) changes, React cleans up the previous effect (running the return function) and runs the effect again.

Q86: How would you optimize the performance of the CodeEditor component?

Currently, every single keystroke triggers a React state update (setValue(value)) and a Socket.io emit. For a massive file, this could cause lag. I would optimize this by:
1. Debouncing the socket emit so it only sends updates after the user stops typing for 100ms.
2. Using React.memo on child components (like LanguageDropdown) so they don't re-render on every keystroke.
3. Instead of syncing the ENTIRE file string on every keystroke, I would implement operational transforms (OT) or send only the line that changed.

SECTION 16: SYSTEM DESIGN & "WHY IS THIS PROJECT BETTER?"

Q87: How does CodeSync compare to Google Docs or standard IDEs? What makes it unique?

CodeSync combines three isolated domains into one unified interface:
1. P2P Video Conferencing (like Zoom/Google Meet) using WebRTC.
2. Real-time Code Editing (like VS Code Live Share) using Monaco and WebSockets.
3. Sandboxed Code Execution (like LeetCode) using Docker/Piston.
Most platforms do one or two of these. CodeSync integrates all three seamlessly in the browser, without requiring the user to download any desktop clients or configure local compilers.

Q88: If you had to replace MongoDB with SQL (PostgreSQL), how would your schema change?

In MongoDB, we just have a JSON document for Users. In SQL, I would create strict tables with relationships:
• Users Table: id (PK), name, email, username, password_hash
• Rooms Table: id (PK), host_id (FK to Users), created_at
• Participants Table: room_id (FK), user_id (FK), role (interviewer/interviewee)
SQL would force me to use complex JOIN operations to load a room's data, which is slower for real-time reads but provides stronger ACID guarantees.

Q89: How does the Piston fallback architecture prove your system design skills?

It shows I understand fault tolerance and high availability. If the local Docker container crashes, runs out of memory, or fails to start, the application doesn't die. The backend catches the fetch failure and gracefully redirects the request to the public Piston API. This ensures zero downtime for the end user during an interview.

Q90: What happens if a user loses their internet connection briefly?

1. Socket.io will automatically detect the disconnect and queue any outgoing messages. Once internet is restored, it automatically reconnects and re-joins the WebSocket room.
2. WebRTC (PeerJS) is more fragile. A network drop will likely sever the P2P connection, freezing the video. The user would need to refresh the page to re-negotiate the WebRTC ICE candidates.

SECTION 17: BEHAVIORAL & THE "GRILLING"

Q91: Interviewer: "I see you used 'last-write-wins' for code synchronization. Isn't that a terrible approach for real collaboration?"

"You are completely right for a Google Docs scenario. If two people type on the same line simultaneously, one person's changes will be overwritten. However, in the context of a Technical Interview, the behavioral pattern is asymmetrical: the candidate codes while the interviewer watches, or the interviewer pastes a prompt while the candidate watches. For this specific use-case, sending the full string state via WebSockets is highly performant and drastically simpler to implement than complex Operational Transforms (OT) or CRDTs. Engineering is about trade-offs, and this was the right trade-off for an MVP."

Q92: Interviewer: "You used Vite, but Next.js is the industry standard right now. Why didn't you use Next.js?"

"Next.js is fantastic for SEO, Server-Side Rendering (SSR), and public-facing content. But CodeSync is a highly interactive, authenticated Single Page Application (SPA) where 90% of the UI (the code editor, the WebRTC video feeds) strictly relies on client-side browser APIs (like navigator.mediaDevices). Server-Side Rendering provides zero benefit for the interview room and would actually complicate the WebSocket and WebRTC initialization. Vite gives me the raw, blazing-fast client-side React environment that this specific app needs."

Q93: Interviewer: "Your backend Dockerfile exposes port 3000, but your frontend tries to reach it. If I deploy this to AWS, how does the frontend know where the backend is?"

"That's why I separated the configuration using environment variables (VITE_API_URL and VITE_SOCKET_URL). In development, they point to localhost:3000. During the AWS deployment via the CI/CD pipeline, the build step injects the actual production URL of the backend load balancer (e.g., https://api.codesync.com) into the Vite build. The React app is compiled with this production URL baked in."

Q94: Interviewer: "What was the hardest bug you faced while building this?"

"The hardest challenge was managing the state of the WebRTC video streams when toggling the camera on and off. Initially, turning the camera off just stopped the video track locally, but the remote peer's screen froze on the last frame instead of turning black. I had to deep-dive into the WebRTC RTCPeerConnection API to figure out how to use replaceTrack(null) on the videoSender to correctly send a black stream to the remote peer without tearing down the entire connection."

Q95: Interviewer: "If your app goes viral tomorrow and 100,000 users log in, what breaks first?"

"The Node.js backend. Socket.io stores active connections in the server's RAM. 100,000 active WebSockets will exhaust the memory of a single Node process, crashing it. To fix this immediately, I would deploy multiple Node.js instances behind an Nginx Load Balancer and implement the Socket.io Redis Adapter, allowing the different backend servers to pass room messages to each other via a Redis Pub/Sub cluster."

SECTION 18: FINAL CODE COMPREHENSION

Q96: In `server.js`, why do you have both `app.use(express.json())` and `app.use(express.urlencoded({ extended: true }))`?

express.json() parses incoming requests with JSON payloads (like our React frontend fetch requests). urlencoded parses requests coming from standard HTML form submissions. Even though our React app uses JSON, having both is a best practice to ensure the API can handle form-data if we ever expose endpoints to a third-party service or webhook.

Q97: Why do we use `useMonaco` and `loader` in CodeEditor.jsx?

The Monaco Editor is a massive library (several megabytes). Loading it synchronously would block the initial page render, causing a terrible UX. The @monaco-editor/react package uses a lazy-loading loader utility that fetches the Monaco core files from a CDN asynchronously only when the editor component actually mounts.

Q98: What does `peer.on('error')` handle in DataProvider?

PeerJS can throw several errors: browser-incompatible, disconnected, invalid-id, or network errors. If the STUN/TURN servers fail to establish a connection due to strict corporate firewalls, this event catches it. Logging it allows us to debug NAT traversal issues.

Q99: What is the purpose of `socket.on("welcome", (s) => console.log(s))`?

It acts as a health check and heartbeat for the WebSocket connection. If the client sees this log, they can guarantee that the TCP handshake, WebSocket upgrade, and Socket.io internal handshakes all completed successfully.

Q100: Sum up your engineering philosophy based on this project.

"CodeSync reflects a pragmatic engineering philosophy: choose the right tool for the job, isolate complex domains, and prioritize user experience. I chose Vite for raw developer speed, MongoDB for agile document-schema iteration, WebRTC to keep heavy video traffic off my servers, and Docker to perfectly sandbox untrusted code execution. It's built to be scalable, secure, and instantly collaborative."

SECTION 19: PROJECT ARCHITECTURE & DIRECTORY STRUCTURE

Q101: "Walk me through the project. What is the directory structure, and what are all these folders and files doing?"

Here is a complete breakdown of the CodeSync repository architecture. It is organized as a monorepo containing both the backend and frontend, along with CI/CD configurations.

1. Root Level (DevOps & Configs)

  • Jenkinsfile / azure-pipelines.yml: CI/CD pipeline definitions for automated building and deployment.
  • docker-compose.yml: Used to spin up the entire application stack (frontend, backend, database) in isolated containers locally for testing.
  • .github/: GitHub Actions workflows for automated testing and linting on pull requests.

2. Backend Directory (/backend)

This is our Express.js and Node.js server handling API requests, WebSockets, and database operations.

  • server.js: The main entry point. It initializes Express, connects to MongoDB, sets up the Socket.io server for real-time collaboration, and mounts the API routes.
  • controllers/: Contains the core business logic. E.g., authControllers.js handles the actual validation, password hashing, and JWT generation for user login/signup.
  • routes/: Defines the API endpoints and maps them to controllers.
    • auth.js: Routes for /login and /signup.
    • execute.js: Routes for handling code execution requests via Docker or Piston API.
  • db/: Database configuration.
    • connectDb.js: Establishes the Mongoose connection to MongoDB Atlas.
    • model.js: Defines the Mongoose schemas (e.g., User schema).
  • Dockerfile: Defines how to build the backend Node.js image for production.

3. Frontend Directory (/frontend)

This is the React.js client built with Vite and styled with TailwindCSS.

  • src/main.jsx & src/App.jsx: The root React components that bootstrap the application and define routing.
  • src/components/: Reusable UI pieces.
    • CodeEditor.jsx: Integrates the Monaco Editor and handles WebSocket code syncing.
    • AudioVideoScreen.jsx: Manages WebRTC PeerJS connections for real-time video streaming.
    • Output.jsx, LanguageDropdown.jsx: UI for code execution results and language selection.
  • src/pages/: Top-level route components.
    • Homepage.jsx: The landing page UI.
    • Login.jsx / Signup.jsx: Authentication pages.
  • src/context/: React Context API files.
    • DataProvider.jsx: Provides global state (like user data, WebRTC peer instances, socket connections) to all components to avoid prop drilling.
  • vite.config.js & tailwind.config.js: Configuration for the Vite bundler and Tailwind utility classes.
  • Dockerfile: Defines how to build and serve the static React frontend (often using Nginx in production).
